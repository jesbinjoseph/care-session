Safety boundary

Use synthetic records only. Never connect this workshop stack to production databases, buckets, Redis instances, APIs or credentials.

06 · Operate the instance

What will you check and recover?

Practice an operator routine and record results in the worksheet. A running container is not enough.

01
Check

API and frontend respond; Beat and worker are running

02
Verify data

Save and reopen a synthetic record; upload and retrieve a test file

03
Diagnose

Inspect the first failing dependency, then downstream logs

04
Preserve

Stop and restart; prove local data survives; plan a separate restore test

For the synthetic workflow, follow the local fixture preparation before signing in. It temporarily supplies a development-only dependency.

docker compose ps -a
docker compose logs --tail=200 beat
docker compose logs --tail=200 backend worker
07 · Extend CARE

Plugs live in the image

Plugs are Django extensions installed at build time—not independent runtime services.

SHARED CARE IMAGE
Backend API
Celery worker
Celery Beat
CARE plugs

One artifact, multiple roles

The API, worker and Beat must run the same tested, plug-enabled image. Compose changes only the process entry point.

ADDITIONAL_PLUGS=[]
docker compose build --no-cache backend worker beat
docker compose up -d --wait
08 · Hosting decision

Choose the platform; keep the responsibilities

A workstation, VM, server, or cluster can host an instance. For each role, decide who runs it, checks it, and restores it.

frontend→Build-time API URL · static serving · browser reachability
backend · worker · beat→Three supervised roles from one pinned image
database · files · broker→Compatible services · backups · named owners
local ports→DNS · TLS · restricted networking · alerting
Write your plan

Use the operator worksheet to assign owners, evidence, recovery objectives, and open compatibility checks.
